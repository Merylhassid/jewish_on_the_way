### 0.6 Google Sign-In — נדחה לגרסה עתידית
החלטה מאושרת: גרסה 1.0 תושק עם אימייל וסיסמה בלבד. נבדקו כל מסכי האימות; רק ב-`login.tsx` וב-`register.tsx` קיים קוד Google, ובשניהם `ENABLE_GOOGLE_AUTH = false`, כך שהכפתור אינו מוצג למשתמש. הקוד נשאר כבוי לצורך אפשרות הפעלה בגרסה עתידית.

בהפעלה עתידית יהיה צורך ליצור Android client ID (עם SHA-1 של keystore ה-EAS) ו-iOS client ID, לעדכן את ה-backend ל-audience המתאים, ולטפל גם בסעיף 0.7.

### 0.7 Apple Sign-In — לא נדרש בגרסה 1.0
גרסה 1.0 אינה מציעה Google Sign-In או התחברות באמצעות ספק צד שלישי אחר, ולכן לא מוסיפים כרגע Sign in with Apple. אם Google Sign-In יופעל בגרסה עתידית, ייבדקו מחדש דרישות החנות ויוגדרו `expo-apple-authentication`, endpoint בבקאנד ו-Capability בחשבון המפתח.

### 0.9 פרטיות ושמירת לוגי אבטחה 🔄 מוכן בקוד, דורש הגדרת שרת בפריסה
- ✅ אירועי Audit אינם שומרים עוד כתובת אימייל קריאה. אירועים רגילים נשמרים עם `userId` בלבד.
- ✅ ניסיונות כניסה ובקשות איפוס סיסמה נשמרים עם `emailFingerprint` מסוג HMAC-SHA256, כדי לזהות דפוס תקיפה בלי לחשוף את האימייל.
- ✅ המפתח המועדף הוא `AUDIT_FINGERPRINT_SECRET`; קיים fallback ל-`JWT_SECRET` לתאימות בלבד. בפרודקשן חובה להגדיר מפתח Audit אקראי ונפרד.
- ✅ קיימת הגנה נוספת ב-`AuditService` שמסירה שדה `email` גולמי אם יועבר בטעות בעתיד.
- ✅ הוסרו כתובות אימייל גלויות וטוקן איפוס גם מלוגי `MailService` ו-`AuthService`; הודעות תפעוליות נשמרות ללא כתובת הנמען, ושגיאת איפוס מזוהה באמצעות `userId` בלבד.

**צ'קליסט חד-פעמי בזמן הפריסה לשרת:**
1. להגדיר `AUDIT_FINGERPRINT_SECRET` קבוע וסודי בסביבת הפרודקשן.
2. להתקין `pm2-logrotate` אם אינו מותקן: `pm2 install pm2-logrotate`.
3. להגדיר סיבוב יומי: `pm2 set pm2-logrotate:rotateInterval "0 0 * * *"`.
4. לשמור לכל היותר 90 קבצים מסובבים: `pm2 set pm2-logrotate:retain 90`.
5. להפעיל דחיסה: `pm2 set pm2-logrotate:compress true`.
6. לאמת את ההגדרות באמצעות `pm2 conf`. אין למחוק ידנית לוגים קיימים; הם ייצאו מהמחזור אוטומטית לפי מדיניות השמירה.

## שלב 2 — קבצי Build

### אנדרואיד (.aab חתום)
```powershell
cd mobile
eas build --platform android --profile production
```
מורידים את ה-.aab מהדשבורד של Expo ומצרפים לתיקיית ההגשה.

### iOS
המסמך של המכללה מבקש דחיפה מ-Xcode עם חשבון המפתח שלהם. עם Expo יש שתי אפשרויות — **לתאם איתם מראש (חלק מ-0.2)**:
1. `eas build --platform ios` — דורש שיוסיפו אותך ל-Apple Developer Team שלהם (או App Store Connect API key), ואז `eas submit`.

## שלב 4 — מדיניות פרטיות (חובה מוחלטת)

1. **לכתוב מסמך** (עברית + אנגלית) — ✅ הושלם כטיוטה בקובצי [`privacy-policy-draft.md`](privacy-policy-draft.md) ו-[`privacy-policy-draft.html`](privacy-policy-draft.html). הטיוטה מכסה אימייל ושם, העדפת כשרות כמידע דתי רגיש, מיקום בזמן שימוש, תמונות, חיפושים, תוכן משתמשים, Anthropic, ספקי שירות, אבטחה, שמירה ומחיקת חשבון. אין לפרסם אותה עד להשלמת רשימת התנאים שבראש הקובץ.
2. **להעלות כדף נגיש** — 🔄 העמוד הדו-לשוני מוכן מקומית ב-`landing/privacy/index.html`, וקישור אליו נוסף לעמוד הנחיתה. לאחר השלמת HTTPS יש לפרסם אותו ב-`https://jewishontheway.com/privacy`.

4. את כתובות ה-privacy והמחיקה מצרפים ל-Metadata ולטופס Data Safety.

לאחר השלמת כל המשימות שהמכללה ביקשה במפורש, נכין גם מסמך עזר עם תשובות ל-**Data Safety** של גוגל ול-**App Privacy** של אפל — רשימת סוגי המידע הנאספים והאם מקושרים לזהות. זהו חומר עזר למילוי טפסי החנויות, ולא סעיף מפורש במסמך המכללה.
