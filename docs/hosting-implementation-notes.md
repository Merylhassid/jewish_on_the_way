## Deviations

### משימה 13 — תוקן גם RTL/LTR ב-`chat/[destinationId].tsx` מעבר לתרגום המחרוזות עצמן

בבדיקת RTL/LTR (הסעיף האחרון של המשימה) התגלה: 16 מקומות ב-stylesheet של הפיד הקהילתי עם `textAlign: 'right'` קשיח (הכותרת, הבאנר, טקסט הפוסטים וכו') — שרידים מכך שהמסך נכתב עברית-בלבד לפני המשימה. גיליתי גם ש-`i18n/index.ts` מגדיר `lng: 'en'` כברירת המחדל האמיתית של האפליקציה — כלומר לפני התיקון, משתמש חדש (אנגלית כברירת מחדל) היה רואה טקסט עברי קשיח *וגם* יישור ימני קשיח בפיד הקהילתי, גם אם כל שאר האפליקציה אצלו באנגלית.

**נבחר (שמרני, בתוך scope המשימה):** הוחלף `textAlign: 'right'` ב-`textAlign: 'auto'` בכל מקום ב-stylesheet (16 מופעים, כולל 2 על TextInput שדרשו `'left'|'right'` בפועל — לכן שם נקבע דינמית לפי `i18n.language === 'he' ? 'right' : 'left'` כי TextInput לא תומך ב-`'auto'` ב-RN). `'auto'` שומר על יישור ימני לתוכן עברי ומתקן ליישור שמאלי לתוכן אנגלי/צרפתי אוטומטית, בלי לגעת במבנה.

**לא תוקן (מחוץ ל-scope):** מיפוי `flexDirection: 'row-reverse'` ו-`alignItems: 'flex-end'` הקבועים במקומות אחדים ב-stylesheet (למשל `statusRow`, `headerTitleBlock`) — אלה הפכי-כיוון אמיתיים של הלייאאוט (לא רק יישור טקסט), ותיקון מלא שלהם דורש היגיון RTL-מודע בכל הקומפוננטה (או אימוץ `I18nManager.forceRTL` ברמת האפליקציה — לא קיים היום בפרויקט בכלל, נבדק ואומת). זה חורג משמעותית מ"i18n + שינוי תווית" ומצריך עבודת UI/QA נפרדת. מתועד כאן לביקורת/משימה עתידית — לא נבנה עוקף.

### ⚠️ גילוי חשוב — `npm run build` שקט על no-op בגלל tsbuildinfo מיושן

תוך כדי בדיקת runtime לשלב 3 גיליתי ש-`npm run build` (nest build) **דיווח הצלחה בלי לפלוט כלום ל-`dist/`** (רק תיקיית `ai/` המועתקת כ-asset) — כי `tsconfig.build.tsbuildinfo` (קובץ cache incremental, **מנוהל ב-git** בפרויקט הזה) היה במצב לא תואם לתיקיית `dist` שנמחקה ע"י `deleteOutDir: true` ב-`nest-cli.json`. tsc, בהתבסס על ה-cache, חשב שאין מה לקמפל מחדש — למרות ש-`dist` היה ריק בפועל.

**המשמעות:** לאורך כל השיחה, בדיקות "npm run build הצליח" (ריצות רבות, שלבים 1-2) יכלו להיות false positive — ההצלחה שיקפה "אין שגיאות קומפילציה שנבדקו" ולא בהכרח "dist מלא ותקין". **בדיקות `npx tsc --noEmit -p tsconfig.json`** (שהרצתי אחרי כל שינוי) **כן היו אמינות** — אלה משתמשות ב-tsconfig נפרד (לא tsconfig.build.json) והראו שגיאות אמיתיות שהופיעו ונעלמו לאורך העבודה (למשל: kashrut_level type union, isolatedModules ב-DTOs) — כלומר בדקו את הקוד בפועל, לא היו no-op.

**תוקן:** `rm -f tsconfig.build.tsbuildinfo && rm -rf dist && npm run build` — בנייה נקייה מאומתת (dist מלא, 100+ קבצים). גם הרצתי בדיקת runtime אמיתית (`node dist/main.js` עם timeout) פעמיים לאורך שלב 3 — כל המודולים עולים בלי שגיאות DI, כל ה-routes נרשמים.

**המלצה למשתמש (לא בוצעה — משנה תשתית build, מחוץ לתחום הפיצ'ר):** לשקול הוצאת `tsconfig.build.tsbuildinfo` מ-git (להוסיף ל-`.gitignore`) כדי שלא יגרום לבעיה דומה בסביבות אחרות (כולל בפריסה לשרת — ראו [[deploy_verify_before_restart]], זו בדיוק הסכנה שתועדה שם).

### משימה 6 — `hosting_type` הפך לשדה חובה ב-`createRequest`, לא אופציונלי

התוכנית לא ציינה אם `hostingType` חובה או אופציונלי בבקשת אורח (`POST /hosting/requests`). **נבחר:** שדה חובה (`@IsIn(['stay','meals'])` בלי `@IsOptional`), עקבי עם שדות דומים כמו `withChildren`/`forShabbat` שכבר חובה ב-DTO הזה. מכיוון שהאפליקציה עדיין לא בחנויות (Expo Go בלבד, [[feedback_expo_mobile]]) אין בעיית תאימות לאחור עם גרסאות ישנות בשטח — כל קריאה ל-endpoint הזה עודכנה באותו commit.

### משימה 6 — באג ב-TypeORM type inference שהתגלה תוך כדי (לא קשור ישירות ל-hosting_type)

הרצת המיגרציה נכשלה בהתחלה עם `DataTypeNotSupportedError: Data type "Object" ... kashrut_level`. הסיבה: תיקון הטיפוס `kashrut_level: string | null` שנעשה במשימה 5 (כדי לתמוך ב-null בעריכה) גרם ל-TypeScript לפלוט `design:type: Object` במטא-דאטה (איחוד טיפוסים לא משתקף כטיפוס יחיד), ו-TypeORM לא הצליח להסיק ממנו עמודת SQL. **תוקן:** נוסף `type: 'varchar'` מפורש ל-`@Column` של `kashrut_level` (כמו ש-`notes` כבר היה עם `type: 'text'` מפורש). לקח לתשומת לב: כל עמודת TypeORM עם טיפוס TS מאוחד (`X | null`) חייבת `type:` מפורש בדקורטור, אחרת רק תתגלה בזמן הרצת מיגרציה הבאה.

### משימה 10 — `is_disabled` נפרד מ-`isActive` הקיים, לא נעשה שימוש חוזר

בזמן המימוש גיליתי endpoint אדמין קיים ולא מחובר ל-UI: `DELETE /admin/users/:id` (`AdminService.blockUser`) שכבר "חוסם" משתמש ע"י `isActive=false` — **אותו שדה** שמייצג גם "אימייל לא מאומת" (`register` יוצר `isActive:false` עד `verifyEmail`). זו בעיה: `resendVerification` שולח קוד חדש לכל משתמש עם `isActive=false` בלי קשר לסיבה, ו-`verifyEmail` מפעיל בחזרה `isActive=true` ללא תנאי — כלומר משתמש שנחסם ע"י אדמין דרך ה-endpoint הישן יכול תיאורטית "לבטל את החסימה" בעצמו רק ע"י בקשת קוד אימות חוזר ואימות מחדש.

**נבחר (לפי התוכנית, שמרני):** שדה חדש ונפרד `is_disabled` (לא נוגע ב-`isActive` הקיים), נבדק בנפרד ב-`login`/`refresh`/`googleLogin`. **לא תוקן** ה-endpoint הישן `DELETE /admin/users/:id` וה-bug הפוטנציאלי בו — מחוץ לתחום פיצ'ר האירוח, ומתועד כאן להעברה לביקורת נפרדת. מסך האדמין החדש שבניתי ("Users" tab) משתמש **רק** ב-`is_disabled` (`POST /admin/users/:id/disable`), לא ב-endpoint הישן.

### משימה 11 — נבחר לא להוסיף `GET /hosting/requests/:id`

כדי לממש "כפתור חסימה" בצ'אט האירוח המובייל היה צריך לדעת את ה-ID של המשתתף השני. שקלתי endpoint REST חדש (`GET /hosting/requests/:id`) אבל בחרתי בפתרון זול יותר: הרחבתי את `hosting-chat:join` (שכבר טוען את ה-request עם היחסים הרלוונטיים) לשדר גם `hosting-chat:participant` עם פרטי הצד השני — משתמש בנתונים שכבר נטענו, בלי query או endpoint נוסף.

### משימה 1 — עמודת `need_id` חדשה (לא הוזכרה בתוכנית)

התוכנית לא ציינה מיגרציה למשימה 1, אבל המימוש דרש דרך לקשר בקשה שנולדה מצורך בחזרה לצורך המקורי — כדי (א) לחסום מארח שכבר הגיב לאותו צורך, ו-(ב) למצוא ולדחות בקשות pending אחרות על אותו צורך כשהאורח מאשר אחת.

**נבחר:** עמודת `need_id` (int, nullable, FK ל-`hosting_needs.id` עם `ON DELETE SET NULL`) בטבלת `hosting_requests`, במיגרציה רגילה (`1789000000000-AddHostingRequestNeedId.ts`) שהורצה על ה-DB החי ב-Neon. זו התוספת המינימלית ביותר — עקבית לגמרי עם דפוס `host_id` הקיים באותה טבלה.

**הערה:** גיליתי בזמן העבודה שטבלת `hosting_needs` ועמודות כמו `host_id`, `guest_hidden`, `host_hidden`, `offer_id` (nullable), `kashrut_level`, `notes` **מעולם לא הופיעו בקובצי מיגרציה** למרות ש-`synchronize: false` — כלומר הן הוזנו ל-DB החי ישירות (כנראה דרך `synchronize: true` זמני או SQL ידני) ללא רישום ב-git. המשכתי עם הדפוס התקין (מיגרציה מתועדת) להוספה החדשה שלי, אבל זה אומר שסכימת ה-DB האמיתית לא לגמרי משוחזרת מההיסטוריה של migrations/.

### משימה 13

- "HOSTING"/"ADMIN" (וה-eyebrow labels הדומים) **לא** תורגמו במכוון — מצאתי תקדים ב-`compass.tsx` (`JEWISH ON THE WAY`) שהאפליקציה כבר משאירה eyebrow labels סגנוניים כאלה קבועים באנגלית בכל השפות (זהות מותג, לא תוכן). עקבתי אחרי אותה קונבנציה.
- ב-`getCategory()` (זיהוי קטגוריה אוטומטי לפי תוכן הפוסט בפיד הקהילתי) יש מילות מפתח בעברית ואנגלית קשיחות (`'מלון'`, `'hotel'` וכו') — **לא** תורגמו. אלה לא טקסט UI אלא לוגיקת ניתוח-תוכן שמחפשת מילים בתוך מה שהמשתמש הקליד בפועל (יכול להיות בכל שפה) — לא שייך ל-i18n.
- שדות dynamic ב-Alert (למשל אזהרת חפיפה, חסימת משתמש) עברו ל-interpolation של i18next (`{{name}}` וכו') — לא היה בשימוש בפרויקט לפני כן (נבדק: אין תקדים), אבל `interpolation: { escapeValue: false }` כבר מוגדר ב-`i18n/index.ts` אז זה עבד ישר בלי שינוי קונפיג.
- כמה מפתחות חדשים תחת `hosting.*` (כמו `cancelBtn`, `deleteBtn`) חופפים סמנטית למפתחות קיימים תחת `common.*` (`common.cancel`, `common.delete`) שגיליתי **אחרי** שכבר כתבתי את מפתחות ה-hosting. לא אוחד בדיעבד — שתי הגרסאות תקינות ומתורגמות נכון בשלוש השפות, זו רק כפילות סמנטית קלה שלא משפיעה על התנהגות. בקומפוננטת הפיד הקהילתי (`chat/[destinationId].tsx`) כן השתמשתי ב-`common.cancel`/`common.delete` הקיימים במקום ליצור כפילות נוספת, ברגע שגיליתי אותם.

### משימה 12

- הבדיקה מבוססת על `user.isActive` (לא שדה חדש) — כי זה **כבר** המנגנון האמיתי של "אימייל מאומת" בפרויקט: הרשמה יוצרת `isActive:false`, `verifyEmail` הופך ל-`true`. מכיוון ש-`login()` כבר חוסם `!isActive`, כל בקשה עם JWT תקף כבר "אמורה" להגיע ממשתמש מאומת — הבדיקה ב-hosting.service היא **הגנת עומק** למקרה של JWT ישן שעדיין תקף אחרי שהחשבון בוטל (`deleteCurrentUser` גם מכבה `isActive`) או נחסם דרך ה-endpoint הישן שתועד במשימה 10.
- `respondToNeed` לא טען את רשומת המשתמש של המארח בכלל לפני כן — נדרשה תוספת `findOneOrFail` כדי לבדוק שם את `isActive`.

### משימה 11

- אכיפת חסימה דו-כיוונית דורשת גישה הדדית בין `HostingModule` ל-`UsersModule` — `UsersModule` מייצא כעת את `UsersService` (`exports:`) ו-`HostingModule` מייבא אותו. נבדק שאין תלות מעגלית (UsersModule לא מייבא את HostingModule בחזרה, רק את ה-entity `HostingRequest`) — אומת גם ב-boot אמיתי (`node dist/main.js`), לא רק ב-tsc.
- חסימה מבטלת התאמה חיה: המימוש טוען את **כל** הבקשות הפעילות (`pending`/`approved`) וסינון בזיכרון לפי הזוג החוסם/נחסם, במקום שאילתת SQL עם תנאי OR מורכב על `guest_id`/`offer.user_id`/`host_id` — פחות יעיל בקנה מידה גדול, אבל הטבלה קטנה וזו פעולה נדירה (בזמן חסימה בלבד), ופשוט משמעותית יותר לקריאה/תחזוקה.

### משימה 7

- "De-dup: לא לשלוח פעמיים על אותו זוג צורך↔הצעה" — **לא** נוספה טבלת דה-דופ ייעודית. ניתוח: זוג (need, offer) יכול להיבדק רק על ידי אחד משני מסלולי היצירה (מי שנוצר **מאוחר יותר** שואל "מי כבר קיים ומתאים עכשיו") — לעולם לא שניהם לאותו זוג באותו אירוע, כי היצירה השנייה היא זו שמריצה את שאילתת ההתאמה. כל לולאת התאמה גם עוברת פעם אחת על שורות ייחודיות (אין אפשרות לשלוח כפול לאותו offer/need בתוך אותה לולאה). לכן הכלל מתקיים באופן טבעי בלי state נוסף. מתועד כדי שסקירת קוד תדע שזו החלטה מודעת, לא פספוס.
- הוספתי `destinationId` ל-payload של שני הפושים (`{needId, destinationId}` / `{offerId, destinationId}`) — לא היה בתוכנית במפורש, אבל בלעדיו אי אפשר לממש את ה-deep-link שהתוכנית כן ביקשה ("עם deep-link"), כי מסך `hosting/[destinationId]` דורש destinationId בנתיב. עודכן ה-listener ב-`mobile/app/_layout.tsx` (שכבר טיפל ב-`requestId`) להוסיף ניתוב ל-host/guest mode לפי הסוג.
- שאילתות ההתאמה עטופות ב-try/catch שקט (best-effort) — כשל בשאילתת ההתאמה לא אמור לעולם להכשיל את יצירת הצורך/ההצעה עצמה.

### משימה 6

- מטריצת ההתאמה (הצעה מכילה בקשה) מיושמת בשלושה מקומות בעקביות: SQL ב-`searchOffers` (`hosting_type IN (:type, 'both')`), ולידציה מפורשת ב-`createRequest`. `respondToNeed` לא צריך בדיקת מטריצה — המארח עונה ישירות לצורך בלי הצעה מתווכת, אז אין "הצעה שצריכה להכיל" את סוג הבקשה.
- "סעודות = תאריך יחיד" מומש כוויתור-על-ולידציה (`validateStayDates`) ולא כאילוץ שוויון קשיח arrival===departure בשרת — כלומר טכנית `meals` יכול לקבל טווח תאריכים אם departure≥arrival, אבל המובייל תמיד שולח תאריך זהה (הבורר היחיד מוסתר). בחירה שמרנית: לא רציתי להוסיף אילוץ נוסף (`arrival === departure` דווקא) שלא נדרש במפורש בתוכנית ועלול לשבור אם מישהו ירחיב את זה בעתיד לטווח קצר של כמה ימי סעודות.
- `SendRequestModal`: כשההצעה מסוג `stay` או `meals` בלבד (לא `both`) — סוג הבקשה ננעל אוטומטית לסוג של ההצעה, בלי selector. רק הצעות `both` מציגות את הבורר לאורח.
- לא הוספתי סינון `hostingType` ל-`listNeeds`/`requestsReceived` — התוכנית לא ביקשה את זה, וההצעה היא זו שצריכה "להכיל" את סוג הבקשה, לא להפך.

### משימה 5 — Post-review fixes (בוצעו ע"י Fable אחרי code review על שלב 1)

בביקורת קוד שנעשתה על שלב 1 (לא על-ידי המבצע המקורי) התגלו 3 בעיות בעריכת הצעה, תוקנו:

1. **קריטי — עריכת הצעה נכשלה תמיד ב-400.** `saveOffer` במובייל שלחה `payload` משותף ליצירה ולעריכה, כולל `destinationId`. `UpdateOfferDto` לא מכיל את השדה הזה, ו-`ValidationPipe` הגלובלי ([main.ts:52-58](../backend/src/main.ts#L52-L58)) עם `forbidNonWhitelisted: true` דוחה את כל הבקשה כשיש שדה לא-מוצהר — לא רק מתעלם ממנו. **תוקן:** `PATCH` שולח payload נפרד בלי `destinationId`.
2. **ניקוי כשרות/הערות בעריכה לא עבד.** אותו payload שלח `kashrutLevel: kashrut.trim() || undefined` — שדה ריק הפך ל-`undefined`, ש-JSON.stringify משמיט, והשרת (`if (dto.kashrutLevel !== undefined)`) מפרש "לא נשלח" כ"לא לגעת". **תוקן:** בעריכה נשלח `kashrut.trim()` (מחרוזת ריקה כשמנקים, לא `undefined`) — כך השרת מבחין בין "לא נגעו" ל"נוקה במפורש".
3. **`updateOffer` לא אכף את מגבלת 3-הצעות/בלי-חפיפה.** הבדיקה קיימת רק ב-`createOffer`; עריכת תאריכים יכלה לעקוף בשקט את הגנת החפיפה שמשימה 5 נועדה להוסיף. **תוקן:** כשהתאריכים משתנים, `updateOffer` בודק חפיפה מול שאר ההצעות הפעילות של אותו מארח ויעד (מחריג את ההצעה הנערכת עצמה) ומחזיר את אותו 409 עם `offerId`.

### משימה 5 — endpoint נוסף שלא צוין בתוכנית: `GET /hosting/offers/:id`

התוכנית ציינה רק `PATCH /hosting/offers/:id`. בזמן המימוש התגלה צורך למשוך את פרטי ההצעה הקיימת לפני עריכה — גם מכפתור "Edit" ב-my-offers.tsx וגם מהניווט "לערוך אותה?" אחרי קונפליקט 409 ביצירה (שם יש לנו רק `offerId`, בלי שאר השדות). **נבחר:** endpoint חדש `GET /hosting/offers/:id` (owner-only, ForbiddenException אם לא הבעלים) — במקום להעביר את כל שדות ההצעה כפרמטרים ב-URL (שברירי ומיותר). נרשם בקונטרולר **אחרי** `offers/mine` ו-`offers/search` כדי לא להתנגש איתם ב-route matching.

גם תוקן אגב־כך: `kashrut_level`/`notes` ב-`hosting-offer.entity.ts` היו מוקלדים כ-`string` (לא `string | null`) למרות שה-DB מאפשר NULL — זה שבר type-check בהקצאה ישירה ב-`updateOffer`. תוקן לטיפוס הנכון; לא משפיע על state בפועל.

### משימה 1

- כלל "חסימת מארח שהגיב פעמיים" יושם באנלוגיה לכלל של משימה 2 (חסימת בקשה כפולה): נחסם רק אם קיימת תגובה `pending`/`approved` פעילה לאותו צורך; אחרי `rejected`/`cancelled` מותר להגיב שוב. התוכנית לא פירטה את ההתנהגות המדויקת, אז נבחרה עקביות עם משימה 2.

- פושים: עודכן טקסט ההודעה כשמארח מגיב לצורך (מ"Someone wants to host you" ל-"A host offered to host you — review and approve/decline"), כדי לשקף שהאורח צריך לפעול. נוספו פושים חדשים: למארח כשהאורח מאשר/דוחה, ולמארחים אחרים שנדחו אוטומטית כי צורך נסגר עם מארח אחר.
